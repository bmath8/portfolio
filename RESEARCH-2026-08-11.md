## 2. The WebGPU question — and the trap that applies directly to us

WebGPU reached **universal browser support in late 2025**. Swapping renderers is close to a
one-line import change, and three.js **falls back to WebGL2 automatically**.

**But:** `ShaderMaterial`, `RawShaderMaterial` and **`onBeforeCompile` are not supported on the
WebGPU backend.** They keep working *through the WebGL2 fallback*, which is exactly why it is
dangerous — the page looks correct while silently never taking the WebGPU path.

**We use `onBeforeCompile` twice** — the brain matcap (fresnel rim, cavity, fold tint) and the
tract material (the Gaussian pulse). So for us "just swap the renderer" would be a lie: we would
ship a WebGPU renderer that always falls back. A real migration means **porting both shaders to
TSL**, which is a genuine rewrite, not a flag.

TSL is written as JavaScript function calls (`add()`, `mul()`, `texture()`) and compiles to WGSL
for WebGPU or GLSL for the fallback — one shader source for both backends.

Reported gains **[unverified]**: r184 fixed per-frame allocation churn (240k–500k objects/sec at
1,000 meshes); compute-shader particle systems past 1,000,000 units vs a ~50,000 WebGL ceiling.
Neither matters at our scale — we draw one 39,828-vertex mesh, 26 instanced nodes and one
instanced line bundle. **WebGPU would buy us almost nothing today.** It matters only if we go
after something compute-bound.

## 3. Techniques worth knowing that we do not use

**Gaussian splatting** is the big shift in web 3D. It renders photoreal captured scenes rather
than modelled ones. Now native-ish: submitted to three.js as **PR #33950** (+ SH1–SH3 view-
dependent colour in #34215), landed as a **glTF extension `KHR_gaussian_splatting`**, and shipping
in Babylon.js 8, Apple RealityKit and NVIDIA Omniverse. Production web renderers:
**[Spark](https://sparkjs.dev/)** (World Labs, fuses splats with normal mesh geometry) and
**[GaussianSplats3D](https://github.com/mkkellogg/GaussianSplats3D)** (Kellogg).

*Relevance to us:* **low, and worth saying so.** Splatting shines for captured real places. Our
subject is a synthetic anatomical mesh carrying live data. It would be a technique in search of a
subject — the exact failure this project already made 26 times.

**Where the real gap is instead:** atmosphere. Kage does not out-engineer us, it out-*places* us —
fog, depth haze, terrain, a ground plane. Our cortex floats on flat black. The vendored skills
`threejs-landscape`, `threejs-weather` and `ambient-section-particles` are precisely this, and are
a far better fit than splatting.

## 4. Motion — and one thing that changed in our favour

**GSAP is 100% free, including every plugin** (SplitText, MorphSVG, DrawSVG, ScrollTrigger),
since v3.13, under Webflow's sponsorship. The old paid "Club GreenSock" wall is gone. We already
vendor it.

Landscape:
- **GSAP** — scroll-driven and timeline-heavy motion.
- **Motion** (ex-Framer Motion) — MIT, framework-agnostic, v12.42.2 (30 Jun 2026). React UI transitions.
- **Anime.js** — ~9 kB, simple tweens.
- **Lenis** — the smooth-scroll layer under any of them.

**CSS scroll-driven animations** (`animation-timeline`, `scroll()`, `view()`) now do natively what
we would otherwise write JS for — but they are **Chromium + Safari only**. Firefox still has them
behind a flag as of **Firefox 152 (Jun 2026)**; global support **~82.6%**, and technically *not*
Baseline for that reason. It is an Interop 2026 priority.

**Verdict for us:** keep the JS conductor. It is portable, it already exists, and it is what
drives a camera rather than a DOM property. CSS scroll timelines are a good progressive
enhancement for *DOM* reveals only.

Other Baseline-now CSS worth using: container queries, `:has()`, nesting, Popover API,
same-document View Transitions (Baseline since Firefox 144, Oct 2025). Anchor positioning tipped
Baseline with Firefox 147 (Jan 2026) but Safari is still partial — treat as enhancement.

## 6. No-code / adjacent tools

- **Spline** — browser 3D editor, embed on web. Good for a hero moment; adds a third-party runtime.
- **Rive** — 2D vector + state machines, very fast. Excellent for micro-interactions.
- **Unicorn Studio** — takes a `.glb`, optimises it, gives embed code.

**All three conflict with our zero-third-party-request rule** unless self-hosted. That rule is on
the page as a claim, so this is a real constraint, not a preference. Consensus pattern for 2026 is
hybrid (Spline hero + Rive micro-interactions) — available to us only if we drop or qualify that
claim.

## 7. Recommendations, ranked by value to *this* site

1. **Atmosphere before technology.** The cortex floats on flat black. Fog, depth haze, a ground
   or horizon, and ambient particulate would close more of the perceived gap than any renderer
   change. Skills: `threejs-landscape`, `threejs-weather`, `ambient-section-particles`.
2. **Open the Selected Work layout** so the scroll world is visible between cards. Known
   limitation of v14 — the camera work is currently hidden behind full-width panels.
3. **Use the GSAP we already vendor** for DOM choreography (word-by-word heading reveals). It is
   free now, it is on disk, and hand-rolling this again is how we got here.
4. **Decide on the unused vendor payload** — use GSAP/Lenis or delete all four files.
5. **Do NOT migrate to WebGPU yet.** It buys us nothing at our draw counts and costs a full TSL
   rewrite of both shaders. Revisit only if we go compute-bound.
6. **Do NOT chase gaussian splatting.** Wrong technique for a synthetic data-carrying subject.
7. **Upgrade three.js r168→r184** as routine hygiene — but re-verify the mesh loader and both
   `onBeforeCompile` patches after, since those are the fragile surfaces.
