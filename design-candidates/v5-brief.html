§ 01 Written in Python. Runs on the machine under my desk.

Brian OS — a fleet of 25 agents I actually operate

Running daily Public source 81/81 tests

Twenty-five Python agents run on a schedule on one Windows box. They index my notes, back up state, read my inbox, watch my spending, scan for work, check each other's health, and write me a brief at 07:00. Most of the reasoning is routed to a local model through Ollama, so the thing that runs every morning costs nothing to run. I drive it from Telegram — two-way, so I can ask it a question from my phone in a parking lot and get an answer back.

The rule I care most about is the boring one: nothing sends, spends, deploys, or deletes on its own. Agents write drafts and wait for me. That single constraint is what makes it safe to leave a system running unattended for months, and it is exactly the instinct I would bring to a production system that belonged to someone else.

Health checks run against the fleet on a schedule and repair what they can reach. The rest pages me. Eighty-one of eighty-one tests pass under pytest — I ran the suite and checked the date, 30 July 2026, because a number on a portfolio that nobody can check is just decoration.

§ 02 The story I'd tell in an interview.

Incident report: the guardian that failed quietly

Resolved Root cause found Check written

A process guardian stopped doing its job. It did not crash, it did not throw, and it did not alert — it just sat there looking alive while the thing it was supposed to be managing kept writing. The disk filled. That is the worst kind of failure, because every dashboard you own says green.

I worked it backwards from the symptom to the actual cause rather than clearing space and moving on, recovered the machine, and then wrote the check that catches this exact shape of failure next time — not "is the process alive" but "is the process still doing the work." A silent failure is only allowed to happen once.

SymptomDisk filled on the machine running the fleet
DifficultyThe guardian process was still running — it had simply stopped working. No error, no alert
ResponseTraced it to root cause, recovered the machine, brought the fleet back
Follow-upWrote a liveness check that verifies work is happening, not just that a process exists
TakeawayMonitoring that only asks "is it up?" will lie to you eventually
§ 03 Shipped, then supported live, in front of real people.

Super Bowl LX Squares — real-time pool, run live

Live Public source Ran during the game

A hundred-square pool that a real audience used during an actual Super Bowl. People claim squares, the host locks the board, numbers are drawn at random, and from there the app resolves winners off the live score as the game moves. There's a chat, and there are host controls for the person running the pool.

What I got out of it wasn't the grid — it was being on the hook while people were using it. Once a room full of people is watching a score update, "it works on my machine" stops being a sentence you're allowed to say. It's still up; you can open it right now.

§ 04 Honest status: prototype, not deployed.

Boombox — collaborative listening, in progress

Not deployed Prototype Public source

A prototype for listening to music together: a shared queue, everyone hearing the same thing at the same time. The interesting problem is state. Some of it has to survive a restart — whose queue it is, what's in it — and that lives in Postgres. Some of it is only true while you're connected: who's in the room, who just skipped. That runs over WebSockets with Redis Pub/Sub and is deliberately kept out of the database.

Keeping those two apart is the whole design. The server can go down and come back without anyone losing their queue, and presence never leaves stale rows behind. To be straight with you: this one is not deployed. The source is public and the architecture is real, but I'm not going to call a prototype a product.
